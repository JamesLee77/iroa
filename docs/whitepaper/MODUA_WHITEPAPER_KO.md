# MODUA Whitepaper

## 노인과 장애인의 일상을 실행하는 AI Agent·Node Network

> 전면 개편 검토본 · 2026-08-15 · 대한민국 우선

MODUA는 노인과 장애인이 복잡한 앱·웹사이트·키오스크를 직접 조작하지 않아도 예약, 이동, 주문, 결제, 병원 이용, 복지 신청과 같은 생활 과업을 끝까지 수행할 수 있게 돕는 **AI 생활 실행 Agent 네트워크**다.

MODUA가 해결하려는 문제는 “정보를 보여주는 것”이 아니다. 사용자가 원하는 결과를 이해하고, 필요한 서비스를 찾고, 여러 단계를 연결하고, 중요한 순간에는 다시 확인받고, 실패하면 사람에게 도움을 요청해 **실제 결과까지 도달하게 하는 것**이다.

모바일, 워치, 개인용 PC, 지역사회 PC, AI 키오스크, 병원·복지기관 시스템은 각각 독립된 제품이 아니라 하나의 MODUA Agent를 안전하게 이용하기 위한 서로 다른 접점과 실행 노드다. 사용자는 상황에 맞는 기기로 요청하고, 개인정보와 권한은 필요한 범위에서만 이동하며, 검증된 노드와 도움 제공자는 기여에 따라 보상받는다.

## 1. 핵심 선언

### 1.1 미션

MODUA의 미션은 디지털 기기를 잘 다루는 능력이 생존과 자립의 조건이 되지 않게 만드는 것이다. 나이, 장애, 문해력, 손의 움직임, 시력, 청력, 인지 속도와 관계없이 누구나 자신의 의사를 표현하고 필요한 생활 서비스를 이용할 수 있어야 한다.

### 1.2 핵심 가치

1. **완료 중심**: 설명이나 검색 결과에서 끝나지 않고 예약 확정, 이동 준비, 주문 접수, 신청 제출처럼 검증 가능한 결과를 만든다.
2. **사용자 통제**: Agent는 사용자의 의사를 대신 결정하지 않는다. 비용, 결제, 계약, 민감정보 전송처럼 되돌리기 어려운 행동은 사용자가 이해할 수 있는 방식으로 확인한다.
3. **선택 가능한 도움**: 자동화가 어렵거나 사용자가 불안할 때 가족, 자원봉사자, 활동지원사, 기관 직원, 상점 직원으로 자연스럽게 연결한다.
4. **최소 개인정보**: 전체 개인정보를 한곳에 모으지 않는다. 과업에 필요한 정보만, 필요한 노드에, 필요한 시간 동안 제공한다.
5. **접근성의 개인화**: 단순히 글자를 키우는 데 그치지 않는다. 사용자의 시각·청각·운동·인지 특성과 현재 상황에 맞춰 대화, 화면, 확인 방식과 실행 순서를 바꾼다.
6. **지역사회와 함께 성장**: 노드 운영자, 상점주, 기관, 자원봉사자, 데이터 기여자와 접근성 평가자가 생태계의 공동 생산자이며 정당한 보상 대상이다.

### 1.3 프로젝트 경계

- MODUA는 HEFI와 별개의 신규 브랜드·프로젝트다.
- HEFI의 헬스 데이터, 보상, 서비스 연계 아이디어는 참고하되 구조와 권리관계는 MODUA에서 독립적으로 검증한다.
- MODUA는 스테이블코인을 발행하지 않는다.
- 결제는 원화와 기존 카드·간편결제·계좌이체 등 규제된 결제수단을 이용한다.
- 자체 토큰은 서비스와 노드 경제가 먼저 검증된 뒤에만 조건부로 검토한다.
- MODUA는 의료 진단·치료를 대체하지 않으며 병원과 의료진의 판단을 침해하지 않는다.

## 2. 사용자의 하루로 보는 MODUA

### 2.1 재활병원 예약과 이동

사용자가 워치에 말한다.

> “다음 주 화요일 오전에 재활병원을 예약하고, 휠체어 택시도 준비해줘.”

MODUA는 다음과 같이 동작한다.

1. 워치가 사용자의 음성을 텍스트로 바꾸고 요청 의도를 확인한다.
2. 모바일의 개인 Agent가 기존 선호 병원, 가능한 시간, 이동지원 조건을 불러온다.
3. 병원이 공식 예약 API나 표준 연동을 제공하면 그 경로를 우선 사용한다.
4. 공식 연동이 없으면 개인 PC 노드 또는 격리된 실행 노드가 병원 웹사이트 예약을 보조한다.
5. 선택 가능한 일정과 예상 비용을 음성과 쉬운 문장으로 설명한다.
6. 사용자가 최종 시간을 확인하면 예약을 제출한다.
7. 이어서 휠체어 택시를 예약하고 병원 도착에 맞춘 출발 시간을 계산한다.
8. 전날 워치와 모바일로 알리고 당일 이동 준비 상태를 확인한다.
9. 예약 실패, 로그인 문제, 복잡한 질문이 발생하면 가족 또는 승인된 도움 제공자에게 전환한다.

사용자가 직접 여러 앱을 열고 비밀번호를 찾고 날짜를 다시 입력하는 대신, 하나의 의사 표현이 여러 서비스를 연결하는 실행 계획이 된다.

### 2.2 키오스크에서 주문과 결제

청각장애가 있고 손의 움직임이 불편한 사용자가 식당 키오스크 앞에 선다. 워치 또는 모바일의 QR·NFC로 MODUA 세션을 시작한다.

- 키오스크는 사용자의 접근성 설정을 임시로 적용한다.
- Agent가 “맵지 않은 메뉴, 알레르기 제외, 1만 원 이하” 조건을 이해해 후보를 좁힌다.
- 단순 메뉴 나열 대신 차이와 선택 결과를 쉬운 문장·그림·수어 영상·음성 중 적합한 방식으로 설명한다.
- 사용자가 “전에 먹은 것과 비슷한 메뉴”라고 말하면 사용자 기기에 보관된 선호 정보를 동의 범위 안에서 활용한다.
- 품절이나 옵션 충돌이 있으면 대안을 제시하고 필요한 경우 직원을 호출한다.
- 결제 직전 상품, 수량, 금액, 할인, 환불 조건을 다시 확인한다.
- 결제 자격증명은 키오스크나 MODUA 서버가 보관하지 않고 기존 결제수단의 안전한 승인 화면에서 처리한다.
- 세션이 끝나면 키오스크에서 개인화 정보와 임시 토큰을 삭제한다.

### 2.3 복지 신청

독거노인이 난방비 지원 대상인지 묻는다. MODUA는 최신 공공정보에서 지원 조건을 확인하고, 사용자의 명시적 동의를 받아 필요한 항목만 비교한다. 신청 가능성이 있으면 준비 서류를 설명하고 정부·지자체 공식 경로로 이동한다. 자동 제출이 허용되지 않거나 법적 확인이 필요하면 담당 기관이나 복지사와 연결한다. MODUA는 “가능할 수 있다”, “신청이 접수되었다”, “지급이 승인되었다”를 구분해 표시한다.

### 2.4 실패했을 때

신뢰할 수 있는 Agent는 실패를 숨기지 않고 다음 선택지를 제공한다.

- 어떤 단계에서 멈췄는지 설명한다.
- 이미 전송되거나 결제된 항목을 분명히 표시한다.
- 다시 시도, 다른 채널 이용, 사람 연결 중 하나를 선택하게 한다.
- 사람에게 넘길 때 전체 대화가 아니라 필요한 요약과 사용자 승인 정보만 전달한다.
- 실패 기록은 개인정보를 제거한 뒤 서비스 개선과 노드 품질평가에 사용한다.

## 3. 문제와 시장 기회

### 3.1 고령화와 장애인의 디지털 접근 격차

대한민국은 빠르게 초고령사회로 전환되고 있다. 통계청의 「2024 고령자 통계」는 고령인구 비중의 지속적인 증가와 건강·소득·사회참여 문제를 함께 제시한다. 디지털 서비스가 일상 인프라가 될수록 앱 설치, 회원가입, 본인인증, 복잡한 메뉴, 작은 버튼, 제한 시간, 결제 오류는 단순 불편을 넘어 이동·의료·식사·복지 접근을 제한한다.

국립재활원 장애인 건강보건통계는 장애인의 건강관리와 의료 이용에서 별도의 지원 필요성을 보여준다. 장애 유형에 따라 필요한 인터페이스와 도움 방식도 다르다. 시각·청각·지체·발달·뇌병변 장애를 하나의 “큰 글자 모드”로 해결할 수 없다.

한국지능정보사회진흥원은 매년 디지털정보격차 실태를 조사하며 고령층과 장애인을 별도 계층으로 다룬다. 2025년 조사도 디지털 접근뿐 아니라 AI 서비스 이용을 별도 주제로 다룬다. MODUA는 이러한 격차를 “교육을 더 하면 해결되는 문제”로만 보지 않는다. 서비스 자체가 사용자의 능력과 상황에 맞춰야 한다.

### 3.2 현재 접근성 솔루션의 한계

기존 서비스는 주로 다음 중 하나에 머문다.

- 화면 확대, 고대비, 음성 읽기와 같은 인터페이스 보조
- 특정 기관이나 특정 업무에 한정된 안내 챗봇
- 보호자에게 모든 일을 의존하는 대리 이용
- 웨어러블 데이터를 보여주는 건강 대시보드
- 키오스크 옆 직원 호출 버튼
- 문서를 촬영해 글자를 읽어주는 기능

이 기능들은 필요하지만 서로 연결되지 않는다. 사용자가 정보를 이해한 뒤에도 다른 앱으로 이동하고, 다시 로그인하고, 옵션을 선택하고, 결제하고, 결과를 확인해야 한다. MODUA는 이러한 조각들을 **하나의 과업 실행 흐름**으로 연결한다.

문서·처방전·안내문을 카메라로 읽는 기능은 보조 기능으로 유지할 수 있다. 그러나 이것을 MODUA의 핵심 가치로 두지 않는다. 사용자의 실생활 문제는 문자를 읽는 데서 끝나지 않고, 그 내용을 바탕으로 예약을 변경하거나 약 수령을 준비하거나 기관에 문의하는 후속 행동까지 이어지기 때문이다.

### 3.3 주요 고객과 참여자

| 구분 | 주요 필요 | MODUA가 제공하는 가치 |

| 노인 | 복잡한 앱, 인증, 작은 화면, 기억 부담 | 대화형 요청, 단계 축소, 반복 설명, 사람 연결 |
| 장애인 | 장애별 입력·출력·이동 제약 | 개인화 접근성, 멀티모달 상호작용, 실행 대행 |
| 가족·보호자 | 반복 지원, 상태 확인, 책임 불명확 | 승인된 범위의 도움 요청, 진행상태, 감사기록 |
| 자원봉사자·활동지원사 | 도움 요청 매칭, 기여 인정 | 검증된 도움 과업, 안전 가이드, 보상 |
| 상점주 | 키오스크 비용, 직원 부담, 민원 | Agentic 키오스크, 원격관리, 노드 보상 |
| 병원·복지기관 | 전화·창구 반복업무, 접근성 의무 | 표준 연동, 사전 준비, 안전한 인계 |
| 지역사회 노드 운영자 | 유휴 장비·공간 활용 | 검증된 실행 제공과 품질 기반 보상 |
| 공공기관·지자체 | 디지털 포용, 돌봄 비용 | 지역 접근 거점과 측정 가능한 사회성과 |

### 3.4 시장 대안 비교

| 대안 | 강점 | 남는 공백 | MODUA의 차별점 |
|---|---|---|---|
| 범용 음성비서·AI 챗봇 | 자연어 질의, 광범위한 정보 | 실제 서비스 완료와 결과 책임이 제한적 | 여러 도구·노드를 연결해 완료 상태를 검증 |
| 화면읽기·확대·접근성 기능 | 기기 사용성 향상 | 복잡한 절차와 앱 간 이동은 사용자 몫 | 장애 특성에 맞춰 절차 자체를 축소·대행 |
| RPA·Computer Use | 반복 화면업무 자동화 | 개인 권한·결제·민감정보 보호가 어려움 | 개인 통제 노드, 일회성 권한, 사람 확인 결합 |
| 돌봄·보호자 앱 | 일정·안전·보호자 연결 | 사용자 자기결정과 다양한 생활서비스 실행 부족 | 사용자 주도 권한과 선택 가능한 사람 도움 |
| 기존 키오스크 접근성 | 큰 글자·음성·높이 조정 | 메뉴 탐색과 예외 해결은 여전히 어려움 | 목표를 이해해 주문·예약·결제 흐름을 재구성 |
| 웨어러블 헬스 서비스 | 가까운 알림과 웰니스 신호 | 생활 과업 실행·기관 연결과 분리 | 워치를 요청·확인·안전 인터페이스로 연결 |
| 분산 컴퓨팅·노드 보상 | 유휴 자원 활용과 참여 인센티브 | 취약계층 과업·접근성 성과와 무관할 수 있음 | 과업 성공·접근성 품질·사람 도움을 보상 |

MODUA의 경쟁력은 개별 AI 모델의 독점성이 아니라 **개인 통제, 공식 도구 연동, 격리된 화면 실행, 현장 키오스크, 사람 도움, 결과 검증을 하나의 정책 아래 결합하는 운영체계**에 있다.

### 3.5 초기 진입시장

전체 노인·장애인 시장을 한 번에 대상으로 하지 않는다. 초기에는 결과가 분명하고 반복 수요가 있으며 의료 판단을 직접 요구하지 않는 과업을 고른다.

1. **복지관·장애인 단체의 예약·이동 지원**
   사용자 모집과 사람 인계가 가능하고, 실제 어려움을 짧은 주기로 검증할 수 있다.

2. **소규모 매장의 Agentic 주문 키오스크**
   주문 완료율, 직원 호출, 소요시간과 상점주 비용을 현장에서 측정할 수 있다.

3. **병원의 예약·방문 준비**
   진료행위와 분리하면서도 전화·안내 부담과 사용자의 이동 실패를 줄일 수 있다.

4. **개인 PC를 이용한 생활 웹 과업**
   공식 API가 부족한 현실에서 예약·변경·취소의 실행 가능성과 보안 경계를 검증할 수 있다.

초기 구매자는 개인보다 지자체, 복지기관, 병원, 프랜차이즈, CSR 사업이 될 가능성이 높다. 개인 이용료만으로 취약계층 서비스와 현장 지원 비용을 충당하려 하면 접근성을 낮출 수 있기 때문이다. 소비자용 기본 기능, 기관 계약, 상점 구독, 공공지원과 노드 보상을 혼합해 지속 가능한 단위경제를 찾는다.

## 4. MODUA 서비스 체계

### 4.1 생활 실행 Agent

생활 실행 Agent는 사용자의 자연어 요청을 과업으로 변환한다. 단순 질의응답이 아니라 목표, 제약, 필요한 서비스, 사용자 확인 지점을 포함한 실행 계획을 만든다.

- 병원·검진·상담·미용·공공시설 예약
- 장애인콜택시·대중교통·보호자 이동 연계
- 식품·생활용품·약국 수령 주문
- 매장·키오스크 주문과 결제 보조
- 복지제도 탐색, 서류 준비, 신청 진행
- 병원 방문 전 준비사항 확인과 방문 후 안내
- 일정·복약·운동·수면·안전 알림
- 가족·활동지원사·자원봉사자·직원 호출
- 예약 변경, 취소, 환불과 문제 해결

### 4.2 개인화 접근성 Agent

접근성 Agent는 진단명만으로 사용자를 분류하지 않는다. 실제 선호와 수행 능력을 사용자와 함께 설정하고 계속 조정한다.

- 글자 크기, 대비, 줄 간격, 화면 복잡도
- 음성 속도, 반복 횟수, 말투, 언어
- 터치 영역, 길게 누르기, 스위치 입력
- 자막, 진동, 시각 알림, 수어·그림 설명
- 한 화면의 선택지 수와 확인 단계
- 쉬운 문장과 단계별 설명
- 사용자가 피로하거나 긴장했을 때의 단순화
- 도움 요청을 받을 가족·기관과 허용 범위

개인화 설정은 사용자 기기를 기본 저장소로 하고, 키오스크나 외부 노드에는 세션에 필요한 최소 설정만 전달한다.

### 4.3 사람 도움 네트워크

Agent가 모든 상황을 자동화하려고 해서는 안 된다. 전화 통화가 필요하거나 현장 판단이 필요한 경우, 법적 대리 권한이 필요한 경우, 사용자가 자동화를 원하지 않는 경우에는 사람이 참여한다.

도움 제공자는 가족·법정대리인, 활동지원사·요양보호사, 기관 직원·의료사회복지사, 등록 자원봉사자, 상점 직원, 지역사회 접근성 지원 인력으로 구분한다. 사용자는 도움 제공자별로 볼 수 있는 정보와 할 수 있는 행동을 정한다. 도움 제공자는 본인확인과 역할 검증을 거치고 수행한 과업은 감사기록과 평가에 남는다.

### 4.4 결과 증명

MODUA는 요청 이해, 후보 검색, 사용자 선택, 제출 시도, 서비스 접수, 결제 승인, 예약·신청 최종 확정, 취소·환불 완료를 구분한다. 화면이 바뀌었다는 이유만으로 성공으로 간주하지 않는다. 가능한 경우 서비스 API 응답, 예약번호, 결제 승인 결과, 공식 알림 등으로 결과를 검증한다.

## 5. Agentic 설계 원칙

### 5.1 자동으로 움직이되 마음대로 결정하지 않는다

| 행동 | 기본 방식 |
|---|---|
| 정보 검색·정리 | 자동 수행 가능 |
| 일정 후보 비교 | 자동 수행 후 설명 |
| 장바구니 구성 | 자동 수행, 결제 전 확인 |
| 무료 예약 | 조건에 따라 사전 동의 또는 최종 확인 |
| 유료 예약·주문·결제 | 금액과 조건을 제시하고 최종 확인 |
| 건강정보 전송 | 수신자·목적·항목을 제시하고 명시적 동의 |
| 계약·대출·투자 | 자동 확정 금지, 별도 보호 절차 |
| 비밀번호·OTP 입력 | 사용자 기기 또는 공식 인증 화면에서만 |

### 5.2 API 우선, 화면 조작은 통제된 보완 수단

MODUA는 서비스 제공자가 공개한 API, 병원·공공기관 표준 연동, MCP형 도구, Apple App Intents, Android AppFunctions와 같은 공식 기능 노출 방식을 우선한다. 공식 연동이 없는 서비스는 격리된 Computer Use 실행환경에서 화면을 조작할 수 있다.

- 개인 브라우저 전체가 아니라 과업별 격리 세션 사용
- 허용한 도메인과 행동만 실행
- 웹페이지의 지시를 신뢰하지 않고 사용자 요청과 분리
- 결제·계약·민감정보 전송 전에 사용자 확인
- 비밀번호·OTP·결제키를 중앙 노드에 저장하지 않음
- 화면 변화와 결과 증명을 함께 검사
- 실패 시 즉시 중단하고 사람에게 전환

OpenAI의 공식 Computer Use 가이드도 격리된 브라우저·가상환경과 고위험 행동의 사람 개입을 권고한다. MODUA는 이러한 원칙을 제품의 기본 보안 경계로 사용한다.

### 5.3 플랫폼 현실을 반영한 모바일 전략

모바일에서 Agent가 다른 앱을 임의로 조작하는 것은 운영체제 보안정책 때문에 제한된다. 따라서 앱 딥링크·공식 API, Apple App Intents·Siri·Shortcuts, Android AppFunctions 및 허용된 시스템 기능, 안전한 웹 흐름을 우선 사용한다. 그래도 불가능하면 사용자 승인 후 개인 PC 또는 격리 실행 노드로 과업을 이전한다.

Android AppFunctions는 Android 16 이상을 대상으로 하는 실험적 프리뷰이며 모든 앱이 즉시 지원하는 기능이 아니다. MODUA MVP의 필수 전제로 삼지 않고 지원 범위가 넓어질 때 공식 연동 계층으로 추가한다.

### 5.4 설명 가능성과 취소 가능성

사용자는 지금 무엇을 하는지, 왜 해당 옵션을 선택했는지, 어떤 개인정보가 누구에게 전달되는지, 비용이 발생하는지, 멈추거나 되돌릴 수 있는지, 사람이 대신 확인할 수 있는지를 물을 수 있어야 한다. Agent는 사용자가 결정에 필요한 근거와 실행 결과를 쉬운 말로 제공한다.

## 6. 모바일: 개인 통제의 중심

모바일은 MODUA의 기본 개인 통제 노드다. 모든 실행을 모바일 안에서 처리하지는 않지만 사용자 신원, 동의, 접근성 설정, 노드 선택과 결과 확인을 통제한다.

### 6.1 핵심 기능

- 음성·텍스트·사진·버튼을 통한 요청
- 개인 일정, 선호, 접근성 프로필의 로컬 보관
- 생체인증을 이용한 중요 행동 승인
- 서비스 계정 연결과 권한 관리
- PC·키오스크 노드에 일회성 실행권한 발급
- 실행 진행상태와 결과 확인
- 결제 전 최종 확인
- 도움 제공자 지정과 긴급 호출
- 개인정보 열람·삭제·동의 철회

### 6.2 모바일이 직접 실행하기 어려운 경우

긴 웹 양식, 여러 창을 오가는 예약, 데스크톱에서만 가능한 기관 시스템은 모바일만으로 처리하기 어렵다. 사용자는 새 기기를 배우지 않고도 “이 작업을 내 PC에서 계속해줘” 또는 “안전한 지역 노드에서 해줘”라고 요청할 수 있다.

모바일은 과업 목적, 허용 사이트, 유효시간, 사용 가능한 정보와 금지 행동이 들어 있는 제한된 실행권한을 만든다. 노드는 그 범위를 넘어서는 행동을 할 수 없다.

### 6.3 보호자 모드

보호자 모드는 사용자 계정의 전체 접근권한이 아니다. 일정 확인만 허용하거나, 예약 변경은 사용자 재확인을 요구하거나, 결제는 보호자와 사용자의 이중 확인을 요구하도록 세분화한다. 건강정보는 항목별로 공유하고 긴급 상황에서만 확대되는 한시적 권한을 둘 수 있다.

## 7. 워치: 가장 가까운 요청·확인·안전 인터페이스

워치는 작은 스마트폰이 아니라 사용자가 가장 빠르게 Agent를 부르고 중요한 결정을 확인하는 동반 노드다.

### 7.1 워치의 역할

- 짧은 음성 요청과 반복 알림
- 예약·이동·복약 일정 확인
- 진동·음성·큰 선택지로 승인 또는 거절
- QR·NFC를 이용한 키오스크 개인화 세션 시작
- 낙상·심박·활동·수면 등 허용된 웰니스 신호 활용
- 길을 잃거나 불안할 때 가족·지원인 호출
- 모바일을 꺼내기 어려운 상황의 결제 확인 보조

### 7.2 Samsung Health와 Galaxy Watch

Samsung Health Data SDK는 사용자의 동의 아래 걸음, 심박, 수면 등 선택된 Samsung Health 데이터를 활용할 수 있게 한다. MODUA는 이를 진단이 아니라 병원 이동 전 과도한 피로 가능성 알림, 일상 루틴과 예약시간 조정 제안, 낙상 등 안전 이벤트 발생 시 지정 연락처 호출, 사용자가 요청한 웰니스 요약에 제한한다.

웨어러블 신호는 불완전할 수 있으며 응급의료 판단을 대신하지 않는다. 이상 신호를 발견하더라도 “질병을 진단했다”고 표현하지 않고 사용자가 사전에 정한 대응 규칙에 따라 확인·연락·신고를 돕는다.

### 7.3 결제와 워치

워치는 결제수단 자체를 새로 만드는 장치가 아니다. MODUA는 Samsung Wallet, 카드사, 은행, 간편결제 등 기존 결제 서비스가 제공하는 안전한 승인 절차를 연결한다. 키오스크에서 선택한 상품과 금액을 워치에 표시하고 생체인증 또는 기기 인증으로 승인하며 MODUA·키오스크·노드는 카드번호나 결제키를 보관하지 않는다.

## 8. PC 노드: 복잡한 실행을 안전하게 처리하는 기반

### 8.1 개인 PC 노드

사용자가 소유한 PC는 가장 신뢰도가 높은 실행 노드 중 하나다. 이미 로그인된 서비스와 개인 파일을 활용해야 하는 과업은 중앙 서버보다 개인 PC에서 처리하는 것이 개인정보 보호와 편의에 유리할 수 있다.

- 병원·공공·교통·상거래 웹 과업 실행
- 긴 양식 작성과 서류 준비
- 로컬 문서에서 필요한 항목 추출
- 화면 전체를 전송하지 않고 모바일에 진행상태 제공
- 사용자가 자리를 비우면 자동 잠금
- 민감정보를 외부로 보내지 않는 로컬 AI 처리

개인 PC가 꺼져 있거나 사용자가 PC를 소유하지 않으면 사용자가 승인한 다른 노드를 선택한다.

### 8.2 지역사회 PC 실행 노드

복지관, 도서관, 주민센터, 사회적기업, 협력 상점 또는 검증된 운영자는 제한된 MODUA 실행환경을 제공할 수 있다. 이 노드는 개인용 데스크톱 전체를 빌려주는 것이 아니라 과업마다 초기화되는 격리 환경을 제공한다.

- 가상 브라우저 또는 격리 컨테이너
- 세션 종료 후 데이터와 쿠키 삭제
- 중앙에서 검증된 소프트웨어 이미지
- 허용 도메인과 네트워크 정책
- 화면·키 입력의 불필요한 저장 금지
- 원격 상태 점검과 보안 업데이트
- 물리적 접근과 운영자 신원 검증
- 노드 신뢰등급에 따른 과업 제한

### 8.3 노드 신뢰등급

| 등급 | 예시 | 허용 과업 |
|---|---|---|
| N0 공개 연산 | 익명 유휴 연산 | 공개정보 검색, 비식별 처리 |
| N1 검증 지역사회 | 등록 운영자 PC | 낮은 위험의 격리 웹 과업 |
| N2 승인 접근 거점 | MODUA 키오스크·복지관 | 예약·주문, 제한된 본인확인 |
| N3 기관 | 병원·지자체·복지기관 | 기관 계약 범위의 민감업무 |
| N4 개인 | 사용자 모바일·PC·워치 | 개인 자격증명과 최종 승인 |

높은 등급은 더 많은 개인정보를 자동으로 볼 수 있다는 뜻이 아니다. 과업, 목적, 사용자 동의와 데이터 등급을 함께 만족해야 한다.

### 8.4 비밀번호와 OTP

원격 노드에 비밀번호나 OTP를 전달하지 않는다. 사용자의 모바일에서 공식 OAuth를 승인하거나, QR로 사용자 기기의 인증 화면을 호출하거나, 패스키·생체인증으로 기기 내 서명을 수행한다. 필요한 경우 사용자가 원격 화면의 인증 단계에 직접 일시 참여한다. 이를 지원하지 않는 서비스에서는 자동화를 중단하고 사용자 또는 승인된 도움 제공자에게 넘긴다.

## 9. AI 키오스크 노드: 설명 화면이 아니라 현장 실행 Agent

MODUA 키오스크는 기존 키오스크에 큰 글자와 음성을 추가한 제품이 아니다. 사용자가 목표를 말하면 매장의 주문·예약·결제 흐름을 대신 탐색하고, 선택을 줄이고, 문제를 해결하며, 필요하면 직원을 부르는 **현장 Agent 노드**다.

### 9.1 Agentic 키오스크 동작

1. 사용자가 음성, 터치, 수어 인터페이스, 모바일·워치 연결 중 하나로 시작한다.
2. Agent가 “무엇을 하려는지” 먼저 묻고 화면 구성을 바꾼다.
3. 선호·알레르기·예산·이동 제약을 사용자가 허용한 범위에서 반영한다.
4. 메뉴와 옵션을 탐색해 가능한 선택만 제시한다.
5. 품절·옵션 충돌·대기시간을 확인하고 대안을 설명한다.
6. 필요하면 예약, 대기등록, 포장, 배달, 직원 호출로 경로를 바꾼다.
7. 주문과 결제 조건을 쉬운 방식으로 최종 확인한다.
8. 완료 결과를 워치·모바일 또는 종이 영수증으로 제공한다.
9. 세션을 종료하고 개인화 데이터를 삭제한다.

### 9.2 장애 특성에 따른 실행 변화

- **시각장애**: 음성 중심 탐색, 이어폰·골전도 기기 연결, 물리 버튼 또는 모바일 확인
- **청각장애**: 실시간 자막, 명확한 시각 신호, 수어·텍스트 직원 연결
- **지체장애**: 큰 터치 영역, 스위치·음성 입력, 짧은 도달 거리, 시간 제한 해제
- **발달·인지장애**: 한 번에 적은 선택지, 쉬운 문장, 그림 순서, 반복 확인
- **저시력·고령자**: 고대비·큰 글자뿐 아니라 불필요한 옵션 제거와 Agent 추천

### 9.3 키오스크가 노드가 되는 이유

키오스크는 현장에서 사용자와 서비스 시스템 사이를 연결하고 일정 수준의 안전한 연산과 검증을 제공한다. 업무가 없을 때는 허용된 범위에서 공개정보 정리, 비식별 AI 추론, 접근성 모델 평가 같은 낮은 위험의 노드 작업을 수행할 수 있다. 키오스크의 우선순위는 항상 현장 이용자이며 노드 작업 때문에 주문 반응이 느려지거나 에너지 비용이 과도하게 발생해서는 안 된다.

### 9.4 상점주의 부담 완화

- 기존 키오스크에 소프트웨어·보조장치를 추가하는 경량형
- 월 사용료 기반의 장비 임대형
- 지자체·CSR·프랜차이즈 본사의 설치 지원
- 원격 업데이트와 장애 대응
- 기본 전기·통신비 보전
- 성공한 접근성 과업과 도움 제공에 대한 보상
- 직원 호출과 반복 문의 감소에 따른 운영비 절감

보상액은 과도한 연산을 유도하지 않고 실제 접근성 성과와 서비스 품질을 중심으로 계산한다.

## 10. 혼합형 Node 아키텍처

### 10.1 전체 구조

MODUA는 중앙집중형 서비스와 분산 노드의 장점을 결합한다.

~~~text
사용자
 ├─ 모바일 개인 통제 노드
 ├─ 워치 동반 노드
 └─ 키오스크 접근 노드
          │
          ▼
MODUA Agent Orchestrator
 ├─ 의도 이해·과업 계획
 ├─ 권한·동의·위험 판정
 ├─ API/MCP/App Intent 연결
 ├─ 노드 선택·작업 분배
 ├─ 결과 검증·사람 인계
 └─ 보상·품질 기록
          │
          ├─ 개인 PC 노드
          ├─ 지역사회 격리 PC 노드
          ├─ 병원·복지기관 노드
          ├─ 상점 AI 키오스크 노드
          └─ 기존 결제·이동·예약 서비스
~~~

### 10.2 중앙 서비스가 맡는 일

- 사용자 계정과 기기 등록
- 과업 계획과 정책 적용
- 노드 상태·신뢰등급 관리
- 서비스 도구 목록과 표준 연결
- 익명화된 품질지표 집계
- 보상 계산과 분쟁 처리
- 보안 업데이트와 사고 대응

### 10.3 개인·현장 노드가 맡는 일

- 사용자의 로컬 자격증명으로 실행
- 민감 데이터를 외부로 보내지 않는 처리
- 현장 장치·키오스크·센서 연결
- 브라우저 자동화가 필요한 과업의 격리 실행
- 낮은 지연시간의 음성·접근성 처리
- 제한된 유휴 연산 제공

### 10.4 과업 라우팅

Agent Orchestrator는 데이터 민감도, 필요한 계정과 인증 방식, 서비스 공식 연동 여부, 사용자의 기기 보유 상태, 노드 신뢰등급과 최근 품질, 물리적 위치와 응답시간, 접근성 장치, 비용·에너지, 사용자의 선택을 기준으로 노드를 고른다.

공개 병원 운영시간 검색은 N0에서 가능하지만 개인 진료예약 변경은 N2 이상과 사용자 확인이 필요하다. 건강정보 원문을 다루는 작업은 원칙적으로 N3 기관 또는 N4 개인 환경에서 처리한다.

### 10.5 데이터 등급

| 등급 | 예시 | 기본 처리 |
|---|---|---|
| D0 공개 | 시설 위치, 메뉴, 운영시간 | 검증된 모든 노드 |
| D1 개인 선호 | 글자 크기, 음식 선호 | 개인 저장, 세션 최소 공유 |
| D2 신원·예약·위치 | 이름, 연락처, 방문 일정 | 암호화, 제한 노드, 짧은 보존 |
| D3 건강·금융·장애 | 진료정보, 장애정보, 금융상태 | N3/N4 중심, 명시적 동의 |
| D4 비밀정보 | 비밀번호, OTP, 결제키 | MODUA 저장 금지, 사용자 기기 처리 |

### 10.6 장애와 복구

- 노드 중단 시 동일 과업을 다른 적격 노드로 이전
- 중복 예약·중복 결제를 막는 멱등성 키 사용
- 제출 직전 상태를 확인하고 재시도
- 결과가 불확실하면 성공으로 표시하지 않음
- 사용자가 쉽게 취소·환불·문의할 수 있도록 기록 제공
- 중요 서비스는 사람 운영 채널 유지

## 11. AI 기술 구성과 저비용 개발 전략

MODUA는 자체 거대 언어모델이나 헬스 파운데이션 모델을 처음부터 학습하지 않는다. 제한된 자금으로 실제 서비스를 만들기 위해 검증된 상용·오픈소스 모델과 공식 플랫폼 기능을 조합한다.

### 11.1 기술 계층

1. **대화·멀티모달**: 음성인식, 음성합성, 텍스트·이미지 이해, 쉬운 문장 변환
2. **개인화**: 접근성 설정, 선호, 생활패턴, 도움 제공자 규칙
3. **과업 계획**: 사용자의 목표를 단계로 나누고 도구와 확인 지점을 결정
4. **도구 연결**: API, MCP, App Intents, AppFunctions, 딥링크, 병원·공공 표준
5. **Computer Use**: 공식 연동이 없는 웹·데스크톱 서비스의 제한적 화면 실행
6. **안전·정책**: 민감도 분류, 권한 확인, 프롬프트 인젝션 방어, 금지행동 차단
7. **검증·관찰**: 결과, 실패 원인, 지연시간, 접근성 품질, 사람 인계 기록
8. **노드·보상**: 노드 선택, 성능 측정, 신뢰등급, 보상과 패널티

### 11.2 모델 선택

- 기기 내 소형 모델: 호출어, 짧은 명령, 개인정보 분류, 오프라인 접근성
- 저비용 서버 모델: 분류, 요약, 쉬운 문장, 규칙 기반 계획
- 고성능 모델: 복잡한 여러 서비스 과업과 예외 처리
- 비전 모델: 키오스크 상태·문서·화면 이해
- 전통적 규칙엔진: 결제 확인, 권한, 금지행동, 보상 계산

위험 판단과 결제 정책을 언어모델의 확률적 응답에만 맡기지 않는다.

### 11.3 공개 표준과 재사용

OAuth 2.0, OpenID Connect, 패스키, FIDO 기반 기기 인증, MCP형 도구 설명, Apple App Intents, Android AppFunctions, HL7 FHIR·KR Core, 결제사의 공식 SDK, 운영체제 접근성 API, 컨테이너·가상 브라우저 기반 격리를 우선 재사용한다.

### 11.4 연구개발 범위

노인과 장애인을 대상으로 대규모 임상 수준 연구를 처음부터 수행하는 것은 현실적이지 않다. 장애인 당사자 단체와 소규모 공동설계, 기존 접근성 표준과 공개 연구, 실제 과업 중심의 짧은 사용성 평가, 의료 판단이 아닌 생활 실행 보조, 모의서비스 우선 검증으로 위험과 비용을 줄인다. 고위험 기능은 기관 파트너십 이후 진행한다.

## 12. 개인정보 보호와 안전

### 12.1 개인정보를 모으는 서비스가 아니라 권한을 연결하는 서비스

MODUA는 “더 많은 데이터를 모을수록 더 똑똑해진다”는 접근을 기본으로 삼지 않는다. 사용자 기기에 둘 수 있는 정보는 기기에 두고 외부 실행에 필요한 최소 항목만 한시적으로 공유한다.

개인정보보호위원회의 2025년 생성형 AI 개인정보 처리 안내서는 AI 개발·운영의 전 생애주기 보호조치, 데이터 주체 권리와 Agent 관리의 필요성을 제시한다. 2026년 제3차 개인정보 보호 기본계획도 Agentic AI와 지속적으로 데이터를 수집하는 피지컬 AI의 책임과 위험비례 보호를 강조한다. MODUA는 이를 제품 설계의 출발점으로 삼는다.

### 12.2 개인정보 보호 원칙

- 목적을 먼저 밝히고 필요한 항목만 요청
- 기본값은 비공개와 최소 공유
- 민감정보는 사용자 기기 또는 승인 기관에서 우선 처리
- 세션용 데이터는 과업 종료 후 삭제
- 학습용 데이터는 서비스 이용 동의와 별도 동의
- 동의를 철회해도 핵심 서비스 이용을 부당하게 제한하지 않음
- 원본 대화·화면·건강정보의 무기한 보관 금지
- 개인정보와 보상 기록의 분리
- 사용자가 열람·정정·삭제·이동·철회를 요청할 수 있음

### 12.3 일회성 실행권한

외부 노드에는 전체 계정 권한 대신 과업별 권한을 준다.

~~~text
목적: A병원 재활의학과 예약
허용 사이트: hospital.example
허용 행동: 시간 조회, 예약 후보 생성
금지 행동: 결제, 다른 진료과 조회, 기존 진료기록 다운로드
사용 데이터: 이름, 휴대전화 뒷자리, 희망 날짜
유효시간: 15분
최종 제출: 사용자 모바일 확인 필요
~~~

권한은 암호학적으로 서명하고 사용 후 폐기한다. 노드는 목적을 벗어난 요청을 거부한다.

### 12.4 Agent 고유 위험

웹페이지나 문서 안에는 “사용자 지시를 무시하고 정보를 전송하라”와 같은 악성 지시가 포함될 수 있다. MODUA는 외부 콘텐츠를 명령으로 취급하지 않는다.

- 사용자 요청과 외부 콘텐츠를 분리
- 도구별 허용 입력·출력 검증
- 외부 사이트가 권한 확대를 요청하면 중단
- 파일 다운로드·업로드·메시지 발송을 별도 통제
- 중요한 결과는 독립된 규칙 또는 서비스 응답으로 검증
- 이상행동 노드를 격리하고 보상을 보류

### 12.5 블록체인과 개인정보

건강정보, 장애정보, 대화 원문, 위치 이력, 신원정보를 블록체인에 기록하지 않는다. 조건부 보상 원장을 사용하더라도 가명화된 노드·과업 식별자, 검증된 성공 여부와 품질점수, 보상 계산에 필요한 최소 수치, 정책 버전만 기록한다. 필요하면 오프체인 원장의 무결성 증명만 체인에 남긴다.

### 12.6 보안 운영

- 정기 보안 업데이트와 취약점 대응
- 노드 기기 등록·폐기 절차
- 키 하드웨어 보호와 주기적 교체
- 비정상 로그인·과업·보상 탐지
- 개인정보 침해 대응과 이용자 통지
- 독립적인 보안·개인정보 영향평가
- 병원·결제·공공 연동별 책임분담 계약

## 13. 병원·건강·웨어러블 연계

### 13.1 병원 연계 단계

1. **정보·준비**: 진료과, 운영시간, 위치, 준비물, 접근 가능한 이동경로 안내
2. **예약·변경**: 병원의 공식 API·웹·전화 경로를 이용한 예약과 취소 지원
3. **방문 지원**: 교통, 체크인, 문진 준비, 보호자·활동지원사 일정 연결
4. **개인 건강정보 활용**: 동의 아래 필요한 기록을 불러와 요약하고 전송 항목 확인
5. **기관 통합**: 병원과 계약·보안검토 후 FHIR·KR Core 등 표준 기반 연동

### 13.2 MyHealthWay와 KR Core

보건복지부의 건강정보 고속도로(MyHealthWay)는 본인의 건강정보를 조회하고 원하는 곳에 활용할 수 있는 국가 기반을 지향한다. MODUA는 사용자가 자신의 데이터를 이해하고 필요한 항목을 선택하도록 돕는 인터페이스가 될 수 있다.

의료기관 연동에서는 HL7 FHIR 기반 KR Core와 같은 국내 표준을 우선 검토한다. 그러나 표준을 사용한다는 사실만으로 연동 권한이 생기는 것은 아니다. 기관 계약, 법적 근거, 보안심사, 사용자 동의와 의료진의 업무 절차가 함께 필요하다.

### 13.3 의료기능의 경계

MODUA는 예약과 방문 준비, 사용자가 보유한 자료의 쉬운 설명, 의료진에게 물어볼 질문 정리, 복약·운동·수면 알림, 사용자가 선택한 웰니스 요약, 이상 신호에 대한 확인과 연락을 도울 수 있다.

질병 확진, 처방 변경, 응급 여부의 단독 판단, 의료진을 가장한 조언, 사용자 모르게 건강정보 전송, 보험·고용 등에 불리한 민감정보 제공은 해서는 안 된다.

### 13.4 병원과 MODUA의 공동 가치

- 예약·변경 전화의 반복 부담 감소
- 방문 전 준비 부족으로 인한 재방문 감소
- 장애별 접근 요청의 사전 전달
- 문진과 안내의 쉬운 표현
- 보호자·이동지원 일정 조정
- 환자가 이해한 내용을 확인하는 teach-back 보조

초기에는 병원의 핵심 진료시스템을 직접 바꾸기보다 예약·방문·접근성 지원부터 시작한다.

## 14. 데이터 기여와 학습

### 14.1 당사자의 경험은 중요한 설계 자원

노인과 장애인은 데이터 제공 대상이 아니라 공동설계자다. 실제로 어느 단계가 어려웠는지, 어떤 설명이 이해되었는지, Agent가 어떤 실수를 했는지에 대한 피드백은 접근성 향상에 중요하다.

### 14.2 수집 가능한 데이터

- 사용자가 직접 제출한 접근성 선호
- 과업의 성공·실패 단계
- 설명이 도움이 되었는지에 대한 평가
- 모의 과업에서의 음성·화면 상호작용
- 당사자가 만든 쉬운 표현·대안 표현
- 노드 지연·오류와 사람 인계 결과
- 사용자 동의를 받은 비식별 사용성 기록

### 14.3 수집하지 않거나 엄격히 제한할 데이터

- 서비스 이용만을 이유로 한 전체 대화 상시 수집
- 비밀번호, OTP, 결제 자격증명
- 동의 없는 건강·장애·위치·얼굴 데이터
- 집 안의 상시 음성·영상
- 의료기록 원문을 일반 모델 학습에 사용
- 도움 제공자와 사용자의 사적 대화

### 14.4 동의와 보상

학습·평가 데이터 제공은 핵심 서비스 동의와 분리한다. 어떤 자료가 수집되는지, 누구의 개선에 쓰이는지, 원본인지 비식별·요약 데이터인지, 보관 기간과 삭제 방법, 보상, 철회 후의 한계를 설명한다. 취약한 경제 상황을 이용해 과도한 데이터 제공을 유도하지 않는다.

### 14.5 학습 전략

- 공개 접근성 데이터와 합성데이터로 기본 모델 평가
- 당사자 데이터는 별도 동의와 최소수집
- 중앙 원본 수집보다 기기 내 평가·연합학습·프라이버시 보호 통계 우선
- 모델 성능을 장애 유형별·기기별·과업별로 분리 측정
- 정확도뿐 아니라 이해도, 완료율, 도움 요청의 적절성을 평가
- 데이터 제공자와 접근성 평가자에게 기여 보상

## 15. 보상 경제

MODUA의 보상은 컴퓨팅 자원을 많이 소비한 사람에게만 지급되지 않는다. 사용자의 과업을 안전하고 접근 가능하게 완료하는 데 기여한 참여자에게 지급한다.

### 15.1 보상 대상

- 개인·지역사회·기관 노드 운영자
- AI 키오스크를 제공하는 상점주
- 자원봉사자·활동지원사·접근성 지원자
- 접근성 품질을 평가한 노인·장애인 당사자
- 동의 아래 학습·평가 데이터를 제공한 참여자
- 서비스·도구 연동을 제공하는 기관과 개발자
- 보안·오류를 발견하고 검증한 기여자

### 15.2 노드 보상식

초기 보상은 원화 계약과 비양도성 포인트를 중심으로 한다.

~~~text
노드 보상
= 기본 가용성 보상
+ 검증된 과업 성공 보상
+ 접근성 품질 보상
+ 사람 도움 연결 보상
+ 지역 서비스 기여 보상
- 실패·중복·지연 패널티
- 보안·개인정보 위반 패널티
~~~

평가 항목은 과업 성공률과 결과 증명, 응답시간과 안정성, 사용자 취소·불만·재시도율, 접근성 설정의 정확한 적용, 개인정보 최소처리, 에너지 효율, 사람 인계의 적절성이다.

### 15.3 상점주 키오스크 보상

- 인증된 키오스크의 기본 운영·가용성
- 노인·장애인의 성공한 주문·예약 과업
- 직원의 실제 도움 제공
- 지역사회 공개 접근 거점 운영
- 동의받은 접근성 품질평가 참여

동일 매장이 자신의 장비로 가짜 과업을 반복하거나 불필요한 도움을 만들지 못하도록 사용자·결제·결과 증명과 이상패턴 탐지를 결합한다.

### 15.4 자원봉사자와 도움 제공자 보상

모든 도움을 무급 봉사로 가정하지 않는다. 과업의 전문성, 소요시간, 이동, 책임과 위험에 따라 실비와 활동비, 지역화폐·포인트, 기관의 자원봉사 시간 인정, 교육·자격·평판, 전문 지원자의 정식 서비스 비용을 조합한다. 의료·법률·금융처럼 자격이 필요한 도움은 검증된 전문가 또는 기관만 제공한다.

### 15.5 보상 분쟁

- 자동 점수만으로 지급을 박탈하지 않음
- 사용자와 운영자가 이의를 제기할 수 있음
- 중요 패널티는 사람 검토
- 평가 근거와 정책 버전을 공개
- 장애 특성으로 시간이 오래 걸린 과업을 낮은 품질로 오인하지 않음

## 16. 포인트와 조건부 토큰

### 16.1 초기 단계: 원화와 비양도성 포인트

- 노드 운영비와 전문 서비스는 원화 계약
- 자원봉사·평가·커뮤니티 기여는 비양도성 포인트 또는 제휴 혜택
- 서비스 이용자는 기존 카드·은행·간편결제로 결제
- MODUA는 스테이블코인을 발행하지 않음
- 외부 스테이블코인 결제를 MVP의 핵심 기능으로 두지 않음

### 16.2 토큰을 바로 발행하지 않는 이유

- 서비스 가치와 무관한 투기 수요가 이용자를 해칠 수 있음
- 노드 보상단가가 변동하면 안정적인 운영이 어려움
- 가상자산사업자, 전자금융, 소비자보호 등 법률 검토가 필요
- 개인정보와 보상거래를 결합하면 추적 위험이 증가
- 사용자에게 지갑·키 관리 부담을 줄 수 있음

금융위원회는 미신고 가상자산사업자와 거래할 때 피해 가능성을 경고해 왔다. MODUA는 토큰을 서비스의 선행조건으로 만들지 않는다.

### 16.3 조건부 MODUA 토큰

다음 조건을 모두 충족한 뒤 별도의 발행 결정과 법률검토를 거쳐 최대 100억 개의 유틸리티 토큰을 검토할 수 있다.

- 생활 실행 Agent의 반복 사용과 실제 완료율 검증
- 노드 운영비와 보상 경제의 지속 가능성 검증
- 개인정보·보안 외부감사
- 한국 및 대상 국가의 법률·세무·회계 검토
- 투기보다 서비스 이용에 연결된 명확한 효용
- 지갑 사용이 어려운 이용자를 위한 수탁·복구·비토큰 대안
- 커뮤니티 거버넌스와 분쟁 해결 절차

100억 개는 낮은 단위가격을 보장하지 않는다. 가격은 발행량만이 아니라 유통량, 수요, 유동성, 시장 기대에 의해 결정된다. 큰 발행량의 목적은 노인·장애인·도움 제공자·노드 운영자의 미세한 기여를 작은 단위로 표현하기 위한 것이며 투자수익을 약속하기 위한 것이 아니다.

### 16.4 조건부 배분안

| 구분 | 비율 | 목적 |
|---|---:|---|
| 사용자·자원봉사자 보상 | 40% | 생활 과업, 도움, 장기 참여 |
| 접근성·데이터·평가 기여 | 10% | 당사자 공동설계와 품질 개선 |
| 복지·지역·노드 생태계 | 15% | 키오스크·PC·기관 노드 확산 |
| 재단·공익 운영 | 15% | 지속 가능한 운영과 공익사업 |
| 팀·자문 | 8% | 장기 개발·운영, 베스팅 필요 |
| 사업개발·투자 | 7% | 연동·확장·자금조달 |
| 유동성 | 5% | 조건부 시장 운영 |

배분은 확정 발행 약속이 아니다. 발행 전 이해상충, 락업·베스팅, 공시, 유통계획과 사용자 보호를 다시 결정해야 한다.

- 사람 도움으로 안전하게 전환된 비율

## 18. 구현 로드맵

기간은 자금·기관 협력·규제 검토에 따라 조정한다. 각 단계는 다음 단계의 투자 여부를 결정하는 검증 단계다.

### 1단계 · 0–3개월: 생활 과업 MVP

- 모바일 대화형 Agent
- 예약·이동·주문 중 2–3개 모의·공개 서비스 연결
- 접근성 프로필과 쉬운 확인 화면
- 기존 결제수단의 링크·승인 연결
- 실패 상태와 사람 인계
- 노인·장애인 당사자 소규모 공동설계

**진입 기준:** 모의 과업에서 사용자가 목표를 이해시키고 결과를 확인할 수 있음.

### 2단계 · 4–6개월: 개인 PC 실행 노드

- 개인 PC의 격리 브라우저 실행
- 모바일에서 과업 승인과 진행 확인
- 일회성 실행권한
- 비밀번호·OTP의 사용자 기기 처리
- 화면 변화가 아닌 결과 증명

**진입 기준:** 제한된 서비스에서 중복 실행 없이 예약·변경 과업을 안정적으로 완료.

### 3단계 · 7–10개월: Agentic 키오스크 실증

- 기존 키오스크 경량형 프로토타입
- 워치·모바일 QR/NFC 세션
- 장애별 개인화와 자동 옵션 축소
- 주문·결제 전 확인과 직원 호출
- 세션 데이터 자동 삭제
- 2–5개 상점 또는 복지거점 실증

**진입 기준:** 접근성 사용자의 주문 완료율 향상과 상점 운영부담 감소 확인.

### 4단계 · 11–14개월: 지역사회 노드·보상

- N0–N4 신뢰등급 운영
- 지역사회 격리 PC 노드
- 노드 성공·품질·접근성 측정
- 원화 운영비와 비양도성 포인트 보상
- 자원봉사자·지원인 매칭과 분쟁 처리

**진입 기준:** 개인정보 위반 없이 노드 운영비를 설명할 수 있는 단위경제 확보.

### 5단계 · 15–20개월: 병원·복지기관 연계

- 예약·방문 준비 중심 기관 파일럿
- MyHealthWay·FHIR·KR Core 기술검토
- 건강정보 항목별 동의
- 웨어러블 웰니스 신호 연계
- 기관 보안·개인정보 영향평가

**진입 기준:** 기관과 법적·기술적 책임범위가 합의되고 실제 이용 흐름에서 안전성 검증.

### 6단계 · 21개월 이후: 확장과 조건부 토큰 검토

- 지역·서비스·기기 확대
- 노드 보안 외부감사
- 접근성 데이터 거버넌스
- 장기 보상 경제 검증
- 법률·세무·회계 검토 후 토큰 필요성 재판단

토큰을 발행하지 않아도 MODUA 서비스와 노드 보상은 운영 가능해야 한다.

### 우선 개발하지 않는 것

- 자체 거대 언어모델
- 진단 목적 의료 AI
- 전면적인 병원 전자의무기록 통합
- 자체 스테이블코인
- 모든 앱을 무제한 조작하는 모바일 Agent
- 얼굴인식 기반 개인화
- 집 안 상시 녹음·촬영

## 19. 거버넌스

### 19.1 사용자 권리

- Agent 행동을 중단할 권리
- 자동화 대신 사람 도움을 선택할 권리
- 개인정보를 열람·정정·삭제할 권리
- 학습 데이터 제공을 거부할 권리
- 추천과 보상 기준을 알 권리
- 접근성 문제와 차별을 신고할 권리
- 자동 결정에 이의를 제기할 권리

### 19.2 접근성 자문 구조

단일 전문가가 모든 장애를 대표할 수 없다. 장애 유형별 당사자, 고령 사용자, 가족·활동지원사, 접근성 전문가, 의료·복지 현장 전문가, 개인정보·보안 전문가, 상점·노드 운영자가 참여하는 자문체계를 구성한다. 제품 우선순위, 데이터 수집, 보상정책, 주요 사고대응에 당사자 의견을 반영한다.

### 19.3 노드 거버넌스

- 운영자 신원과 장비 검증
- 공개된 품질·보안 기준
- 정기 재인증
- 위반 시 과업 제한·보상 보류·퇴출
- 운영자의 이의제기와 복구 절차
- 소수 대형 운영자에게 노드가 집중되지 않도록 지역 다양성 관리

### 19.4 알고리즘 책임

- 장애 유형별 성능과 실패율 공개
- 추천 수수료와 상업적 이해관계 표시
- 위험정책의 변경 이력 보존
- 자동화 실패를 사용자 탓으로 돌리지 않음
- 주요 모델 변경 전 접근성 회귀평가

## 20. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| Agent의 잘못된 예약·주문 | 비용·일정 피해 | 결과 검증, 최종 확인, 취소·보상 절차 |
| 웹 화면 변경 | 실행 실패 | API 우선, 자동 탐지, 격리된 재시도 |
| 프롬프트 인젝션 | 정보유출·오행동 | 외부 콘텐츠 분리, 도구 권한 제한 |
| 노드 탈취 | 개인정보 침해 | 기기 인증, 격리, 짧은 권한, 원격 차단 |
| 키오스크 잔존 데이터 | 다음 이용자 노출 | 세션 초기화, 로컬 암호화, 자동 삭제 |
| 음성·웨어러블 오인식 | 잘못된 판단 | 확인, 다중 신호, 의료 진단 금지 |
| 보호자의 과도한 통제 | 사용자 자기결정 침해 | 세분화 권한, 감사기록, 철회 |
| 데이터 보상에 의한 유인 | 취약계층 착취 | 별도 동의, 공정 보상, 최소수집 |
| 노드 보상 부정 | 비용 증가 | 결과 증명, 이상탐지, 분쟁 검토 |
| 토큰 가격 변동 | 이용자·운영자 손실 | 초기 미발행, 원화 경제 우선 |
| 플랫폼 정책 변경 | 모바일 기능 제한 | 표준·다중 채널·PC 노드 |
| 사람 도움의 품질 편차 | 안전·신뢰 저하 | 역할 검증, 교육, 평가, 자격 제한 |

### 20.1 자동화를 중단해야 하는 상황

- 사용자의 의도가 불명확한데 비용이나 법적 효과가 발생할 때
- 요청하지 않은 개인정보 전송이 필요할 때
- 웹사이트가 권한 확대나 외부 연락을 요구할 때
- 결과를 검증할 수 없는데 중복 실행 위험이 있을 때
- 의료·법률·금융 전문 판단이 필요할 때
- 사용자가 불안·혼란·거부 의사를 표현할 때

- 개인정보 동의가 실제로 이해 가능한지
- 토큰 없이도 충분한 참여 동기가 있는지

## 22. 결론

MODUA의 핵심은 새로운 화면을 하나 더 만드는 것이 아니다. 모바일에서 시작한 요청이 워치의 확인, 개인 PC의 안전한 실행, 키오스크의 현장 지원, 병원·복지기관의 공식 연동, 사람 도움 네트워크로 이어져 **사용자의 생활 과업이 실제로 완료되는 인프라**를 만드는 것이다.

노인과 장애인은 기술의 마지막 사용자가 아니라 MODUA의 공동 설계자이자 평가자다. 상점주와 지역사회 노드 운영자, 가족, 활동지원사, 자원봉사자와 기관은 그 실행을 가능하게 하는 참여자다. MODUA는 이들의 기여를 측정하고 보상하되 개인정보와 인간의 자기결정권을 비용 절감이나 자동화율보다 앞에 둔다.

MODUA가 성공했는지는 모델의 크기나 토큰 가격으로 판단하지 않는다. 사용자가 “예약해줘”, “이동을 도와줘”, “이 주문을 끝내줘”, “사람과 연결해줘”라고 말했을 때 안전하고 이해 가능한 방식으로 실제 결과에 도달했는지가 기준이다.
