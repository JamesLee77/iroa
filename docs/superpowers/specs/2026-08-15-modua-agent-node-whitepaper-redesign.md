# MODUA Agent 노드 기반 백서 전면 개편 설계

- 문서 상태: 사용자 승인 설계
- 작성일: 2026-08-15
- 적용 대상: `docs/whitepaper/MODUA_WHITEPAPER_KO.md`
- 프로젝트: HEFI와 별개의 신규 브랜드 `MODUA(모두아)`

## 1. 목적

기존 MODUA 백서는 문서 촬영·쉬운 설명·제한적인 모바일 보조 기능에 비해 문서 생성·검증 체계와 안전 경계를 지나치게 크게 다뤘다. 그 결과 사용자가 기대하는 실생활 서비스, 분산 노드 인프라, 키오스크의 Agent 실행 능력과 참여자 보상 구조가 충분히 드러나지 않았다.

새 백서는 MODUA를 다음과 같이 다시 정의한다.

> MODUA는 워치·모바일·개인 PC·AI 키오스크·분산 실행 노드를 연결하여 노인과 장애인의 예약·주문·이동·결제·병원·복지 업무를 실제로 수행하는 AI 생활실행 Agent 네트워크다.

음성, 큰 글자, 쉬운 설명과 문서 인식은 Agent를 이용하기 위한 접근 수단이다. 백서의 핵심 가치는 사용자가 복잡한 화면을 직접 조작하지 않아도 생활 과업을 안전하게 완료하는 데 둔다.

## 2. 확정된 제품 원칙

1. 서비스와 생활 과업 완료가 토큰보다 먼저다.
2. 문서 촬영은 보조 기능이며 핵심 제품으로 제시하지 않는다.
3. 사용자는 목적을 말하고 Agent는 여러 서비스를 연결해 계획·실행한다.
4. 공식 API와 MCP를 우선하고, API가 없는 경우 격리된 Computer Use를 보조적으로 사용한다.
5. 결제·계약·의료정보 전송 등 고위험 행동은 사용자가 기존 인증수단으로 최종 확인한다.
6. 키오스크는 큰 글자 화면이 아니라 공공장소의 Agent 접근·실행 노드다.
7. 노드 보상은 개인정보나 건강데이터의 양이 아니라 검증된 서비스 기여를 기준으로 한다.
8. 개인정보 원문과 민감한 파생정보를 블록체인·보상 원장에 기록하지 않는다.
9. MODUA는 스테이블코인을 발행·수탁·환전하지 않는다.
10. 조건부 MODUA 토큰은 실제 서비스와 노드 경제성이 검증된 뒤에만 검토한다.

## 3. 핵심 서비스

### 3.1 생활 예약·주문

- 병원·복지기관·식당·미용실·공공시설 예약
- 예약 변경·취소·환불 요청
- 음식·생필품 주문과 배송 확인
- 상점 접근성·재고·운영시간 확인

### 3.2 이동 지원

- 택시·장애인 콜택시 호출
- 병원 예약과 이동시간 연계
- 출발·지연 알림
- 보호자·자원봉사자 동행 요청

### 3.3 병원·웰니스 지원

- 진료 일정·준비물·질문 정리
- 사용자가 승인한 복약·생활 요약 전달
- 워치의 걸음·수면·심박 집계정보 확인
- 병원 계약 후 읽기 전용 표준연계 검토
- 진단·처방·응급판정 자동화 금지

### 3.4 복지·공공서비스

- 가능한 복지서비스 검색
- 신청 조건과 준비서류 설명
- 신청서 작성과 방문 예약 보조
- 담당 기관·직원 연결

### 3.5 결제 지원

- 금액·수취인·수수료·정기 여부·환불 조건 설명
- 기존 카드·계좌·간편결제 화면 연결
- 사용자 최종 인증
- 불명확한 결제의 자동 재시도 금지

### 3.6 사람 연결과 상호지원

- 가족·보호자·자원봉사자·직원 호출
- Agent가 해결하지 못한 작업의 안전한 인계
- 이용자와 도움 제공자의 완료 상호확인
- 검증된 도움과 접근성 평가 기여 보상

## 4. 대표 사용자 여정

사용자가 워치를 키오스크에 접촉한 뒤 다음과 같이 말한다.

> “다음 주 화요일 재활병원을 예약하고 휠체어 택시도 준비해줘.”

MODUA는 다음 순서로 처리한다.

1. 워치 또는 모바일에서 일회성 동의와 접근성 설정을 확인한다.
2. 목적을 병원 예약과 이동 예약이라는 여러 과업으로 나눈다.
3. 부족한 조건만 짧게 질문한다.
4. 공식 API·MCP·격리된 Computer Use를 이용해 선택지를 찾는다.
5. 시간·비용·접근성·취소 조건을 비교한다.
6. 예약 초안을 만들고 중요한 조건만 다시 설명한다.
7. 사용자가 예약과 개인정보 전송을 확인한다.
8. 결제가 필요하면 원 서비스의 인증수단으로 사용자가 승인한다.
9. 결과와 변경·취소 방법을 워치와 모바일로 전달한다.
10. 키오스크의 개인 세션정보를 삭제하고 검증된 노드 기여를 정산한다.

- 선택적 웰니스 집계정보 연결

- 개인정보가 제거된 작업 증명으로 보상 정산

## 6. Agent 실행 구조

Agent 실행 조정망은 다음 모듈로 구성한다.

- 의도·목적 분석기
- 다단계 과업 계획기
- 노드 능력·신뢰등급 등록부
- 동의·정책 엔진
- 개인정보 최소화·가명화 모듈
- API·MCP 연결기
- 격리된 Computer Use 실행기
- 결과 검증기
- 작업 이어받기·복구 모듈
- 노드 보상 정산기

실행 순서는 `목적 입력 → 과업 분해 → 위험·데이터 등급 판정 → 노드 선택 → API/MCP 우선 실행 → 필요시 Computer Use → 사용자 확인 → 결과 검증 → 전달·정산`이다.

## 7. 자동 실행 경계

| 단계 | 예시 | 기본 정책 |
|---|---|---|
| 자동 실행 | 공개정보 검색, 비교, 경로 작성, 예약 가능 시간 확인 | 사용자 요청 범위에서 자동 |
| 간단 확인 | 무료 취소 예약, 직원 호출, 도움 요청 | 조건을 보여준 뒤 확인 |
| 본인인증 | 유료 예약, 주문, 결제, 의료정보 전송, 계약 | 원 서비스·모바일 인증 필요 |
| 자동화 금지 | 고액 결제, 처방 변경, 의료 판단, 새로운 개인정보 목적 | 사람·전문기관으로 인계 |

얼굴 인식을 기본 기능으로 사용하지 않는다. 사용자가 워치·NFC·QR로 세션을 시작한 뒤 승인된 범위에서 Agent가 자동 실행한다.

## 8. 데이터·개인정보 구조

| 등급 | 예시 | 허용 위치 |
|---|---|---|
| D0 공개 | 공공정보, 영업시간 | 검증된 모든 노드 |
| D1 개인 설정 | 글자 크기, 음성 속도, 이동 선호 | 개인 노드, 일회성 키오스크 |
| D2 식별정보 | 이름, 연락처, 예약정보, 위치 | 개인·접근·계약 서비스 노드 |
| D3 민감정보 | 건강, 금융, 장애정보 | 개인 또는 승인 기관 노드 |
| D4 비밀정보 | 비밀번호, OTP, 결제키 | MODUA 미보관, 원 서비스 처리 |

보상 원장에는 무작위 작업번호, 노드번호, 성공 상태, 품질점수, 보상액만 기록한다. 이름·음성·건강·위치·예약 내용은 기록하지 않는다.

## 9. 노드 신뢰등급

| 등급 | 운영자 | 처리 범위 |
|---|---|---|
| N0 공개 연산 | 일반 참여자 | 공개·비식별 작업 |
| N1 검증 커뮤니티 | 신원·장비 검증 운영자 | 가명화된 비민감 실행 |
| N2 접근 노드 | 승인 상점·복지기관 | 일회성 사용자 세션 |
| N3 기관 노드 | 병원·지자체·결제기관 | 계약·동의된 민감 업무 |
| N4 개인 노드 | 사용자 본인 | 본인의 개인 데이터·설정 |

낮은 신뢰등급 노드는 높은 데이터 등급을 요청하거나 처리하지 못한다.

## 10. 노드 보상과 상점주 부담 경감

노드 보상은 다음 원칙을 사용한다.

`기본 가동 보상 + 검증된 성공 과업 + 접근성 품질 + 현장지원 − 오류·규칙 위반`

보상 대상은 키오스크 운영 상점, PC형 연산 노드, Computer Use 노드, 기관 노드, 자원봉사자, 접근성 평가자다. 데이터 양과 건강정보의 민감도를 보상 기준으로 사용하지 않는다.

상점주는 고성능 AI 서버를 구매하지 않는다. 저비용 키오스크는 현장 인터페이스와 제한된 로컬 처리만 담당하고, 복잡한 연산은 실행 노드가 분담한다. 무상 설치 또는 저가 임대, 원격 업데이트, 전력·통신 기본 보상, 성공 과업 보상, 지자체·복지기관·CSR 후원으로 상점 부담을 낮춘다. 접근성 사용을 이유로 이용자에게 추가 요금을 부과하지 않는다.

초기 노드 운영비는 계약에 따른 원화로 정산한다. 양도 불가능한 MODUA 포인트는 기여 기록에 사용한다. 최대 100억 개의 조건부 MODUA 토큰은 실제 노드 수요, 지속 가능한 원화 수익, 법률·세무·회계 검토와 보안감사를 모두 통과한 뒤에만 검토한다.

## 11. 장애·오류 처리

- 네트워크 단절: 완료로 추정하지 않고 모바일·개인 PC로 작업 이전
- 노드 응답 실패: 동일 작업번호로 상태만 재확인
- 가격·시간 변경: 자동 확정하지 않고 새로운 조건 재확인
- 결제 상태 불명확: 자동 재결제 금지, `확인 중` 유지
- 음성 오인식: 시간·장소·금액·대상을 다시 읽고 수정
- 키오스크 시간 초과: 세션 잠금과 개인정보 삭제
- CAPTCHA·본인인증: 사용자·직원·원 서비스로 인계
- 악성 노드: 격리, 보상 보류, 영향 범위 조사
- 불확실한 Agent 판단: 추측하지 않고 사람에게 연결

## 12. 구현 단계

### 1단계: 중앙 검증형 MVP

- 모바일 Agent
- 워치 세션·알림
- 키오스크 1종
- 중앙 검증 실행 노드
- 예약·이동·주문 2~3개 과업
- 원화 기반 운영자 정산

### 2단계: 개인 PC·검증 PC 노드

- 개인 PC 로컬 AI
- 비민감 커뮤니티 실행 노드
- 노드 등록·상태·보상
- 키오스크 3~5곳 실증
- 작업 이어받기·복구

### 3단계: 지역 노드망

- 다수 키오스크와 지역 상점·복지기관 노드
- 검증·보상 노드
- API·MCP 파트너 확대
- 상점 운영비 절감과 이용자 효과 검증

### 4단계: 기관 연계

- 병원·지자체·결제기관 노드
- 계약된 의료·복지 연계
- 강화된 장치검증과 감사

### 5단계: 조건부 토큰 검토

- 서비스와 노드 경제성이 원화 기준으로 먼저 성립해야 한다.
- 조건을 충족하지 않으면 포인트·원화 정산 체계를 유지한다.

## 13. 백서 재구성 순서

새 백서는 다음 순서로 다시 작성한다.

1. 한 페이지 핵심 선언과 대표 생활 시나리오
2. 이용자의 실생활 문제와 시장
3. MODUA 생활실행 Agent 서비스
4. 모바일·워치·PC·키오스크 전체 경험
5. 혼합형 분산 노드 아키텍처
6. Agent 실행 기술과 API·MCP·Computer Use
7. 개인정보 보호·동의·데이터 등급
8. 도움 제공자·노드·상점 보상
9. 사업모델과 상점주 비용 경감
10. 포인트·조건부 토큰 경제
11. 단계별 구현 로드맵
12. 안전·규제·오류 대응
13. 근거자료와 HEFI 참고 경계

문서 촬영 시나리오는 생활 기능의 한 사례로만 남긴다. 생성기·검증기·테스트 체계는 백서 본문 주제가 아니며 산출물 품질관리 수단으로만 다룬다.

## 14. 백서 완료 기준

- 첫 두 페이지에서 MODUA가 수행하는 실생활 과업을 이해할 수 있다.
- 예약·주문·이동·결제·병원·복지·도움 연결이 구체적인 사용자 흐름으로 설명된다.
- 모바일·워치·개인 PC·커뮤니티 PC·키오스크·기관·검증 노드의 책임과 경계가 모두 나온다.
- 공식 API·MCP 우선, Computer Use 보조 원칙이 분명하다.
- 개인정보와 노드 보상 데이터가 분리된다.
- 상점주 비용 경감과 노드 운영 보상이 사업모델로 연결된다.
- MODUA가 스테이블코인을 발행하지 않는다는 원칙이 일관된다.
- 조건부 100억 개 토큰은 서비스 검증 이후의 선택지로만 제시된다.
- 시장·플랫폼·웨어러블·의료·규제 주장은 최신 1차 출처로 뒷받침된다.
- HEFI는 참고자료로만 구분되고 MODUA의 독립 브랜드·서비스가 중심이 된다.
- DOCX·PDF 생성과 검증보다 백서 내용의 충실성과 현실성이 우선한다.
